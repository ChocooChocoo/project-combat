# Objective: Next feature set for the Combat Sports Training Center Platform

## Goal

Add a set of enhancements across the gym workspace. They cover navigation, memberships, CRM approvals, history filters, purchasing, notifications, coach applications, athlete goals and safety monitoring. The work must fit the existing Laravel 13 + React architecture, with permissions in `config/permissions.php` and gym separation through `BelongsToGym`.

## Success Criteria

- Each item below works end to end: backend, permission catalog entry, frontend screen and tests.
- New routes use `permission:` middleware, and every new permission string is added to the catalog first.
- Everything is scoped per gym, and the frontend `can()` check mirrors the backend.
- Each item has a phase plan in `docs/implementation-plan/`, with checkboxes kept current.
- Because these features change the system, the documentation is updated to match (see task J):
  - `docs/ANALYSIS - COMBAT SPORTS PLATFORM/`
  - Artifact "Combat Platform Process Guide": [https://claude.ai/artifact/F312k4j7vUEqzDJjjZ8pCP](https://claude.ai/artifact/F312k4j7vUEqzDJjjZ8pCP)
  - Artifact "Combat Gym Testing Artifact": [https://claude.ai/artifact/DWVYNmU1GXfyu8NyV147ed](https://claude.ai/artifact/DWVYNmU1GXfyu8NyV147ed)

## Constraints

- Plan before building. No code changes in this step.
- Notifications are database notifications only, with 15-second polling and no push.
- Scheduled jobs use `Schedule::call(fn () => Artisan::call(...))`.
- Keep `(R-xx)` requirement comments. Do not change unrelated code.
- Money stays in existing formats (decimal for plans and payments, integer centavos for payroll).
- Items marked "notification only" send notices and do not block any action.

## Context

Current state, from reading the code:

- **Sidebar.** `frontend/src/components/gym-nav.tsx` has five groups: People, Training, Members, Business, Setup. People holds Staff, Staff attendance, Leave and Payroll. Finance sits under Business. Payments sits under Members.
- **Workspace persistence.** Only the auth token is saved in `localStorage` (`lib/api.ts`). No selected-gym value is saved.
- **Membership plans.** `membership_plans` has `billing_type`, `duration_months` and `session_count`. `memberships.amount_charged` is stored per membership. There is no advance-payment field.
- **CRM.** The Customers module has `customers.records` and `customers.groups` permissions. No promo or voucher model exists. The `approve` action already exists for bookings, memberships, payroll and procurement.
- **Purchasing.** `purchase_request_lines`, `purchase_orders` and `goods_receipts` tables exist. No receipt-proof or image columns were found.
- **Reminders.** Existing jobs cover membership expiry, session reminders, membership reminders, subscription reminders, follow-ups, no-shows and staff absences. There is no member inactivity monitoring.
- **Coach applications.** `account_type` is fixed as `member` or `owner`. Only owners apply for gyms. `work_schedules` exists for staff.
- **Athletes.** `athlete_profiles` has `current_rank` and `level`. Health data is stored only as intake answers on the membership.
- **No existing model found for:** goals, milestones, injuries or equipment safety.

## Tasks

### A. Sidebar and workspace

- Rename the sidebar sections: "HR / Employee Management" for People, and a "Finance" section. Decide which items belong where.
- Remember the selected gym workspace across login and logout, so the user does not switch again.

### B. Membership management

- Add advance membership plans (for example, pay 3 months in advance).
- Keep a member's price fixed once they have paid. If the gym later changes the plan price, the member is not charged again.

### C. CRM promos and vouchers

- CRM staff can create promos and vouchers. They take effect only after owner approval. The owner can create as well but no approval since it's the owner.

### D. History and date filters

- Add date filters to every history page.

### E. Purchase request and purchase order

- Allow multiple items on one purchase request.
- Allow uploading proof of receipt on a purchase order: a receipt or photos, multiple image files.

### F. Notifications and monitoring (notification only)

- Send automatic expiration reminders.
- Monitor absence and inactivity.

### G. Coach applications

- A member can apply as a coach at a gym.
- The system checks for schedule conflicts with the applicant's schedules at other gyms.

### H. Training goals and milestones

- Add training goals and milestones.

### I. Safety and recovery monitoring

- Injury and recovery monitoring.
- Equipment safety monitoring.

### J. Documentation and artifacts

- Update `docs/ANALYSIS - COMBAT SPORTS PLATFORM/` for every change in sections A to I (new requirements, findings, architecture, diagrams, roadmap, screens by role, word list).
- Update the two artifacts so they match the new behavior:
  - "Combat Platform Process Guide" (public): add the new and changed processes.
  - "Combat Gym Testing Artifact" (owner only): add test steps for the new and changed features.

## Open Questions

- **Advance plan (B):** Does "3 months advanced" mean paying 3 months up front, booking 3 months ahead, or a discount for prepaying?
- **Price lock (B):** Does it apply to renewals only, to instalments, or to both? Does it cover only the current term, or all future renewals?
- **Offers (C):** What do promos and vouchers do? Examples are a percentage off, a fixed amount off, or a code. What do they apply to: plans, services, or both?
- **Offers (C):** Who counts as "the CRM", and which role approves? Is it the owner only, as stated?
- **History pages (D):** Which screens count as "history pages"? A list is needed.
- **Purchase requests (E):** The line table already exists. Is the gap in the UI or in the API?
- **Reminders (F):** What are the reminder lead times? What inactivity threshold applies, and who is notified: the staff, the member, or the owner?
- **Coach applications (G):** `account_type` is fixed and only members join gyms. Does a coach stay a member account and also get an employee link? Who approves the application?
- **Safety (I):** Who records injuries: staff, the athlete, or both? Who may view them, given the health-records permission? How does an equipment check relate to the existing stock items?
- **Documentation (J):** Should the docs and artifacts be updated after each phase or once at the end? The process guide is public, so is it fine to publish updates to it directly?
- **Priority and phasing:** What is the build order? The list has about 9 areas. Should each get its own phase plan?
